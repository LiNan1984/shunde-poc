## 何时使用

当用户需要分析、解释或可视化来自 SQL、电子表格、笔记本、仪表板、导出或临时表的数据时使用此技能。

用于 KPI 调试、实验报告、漏斗或队列分析、异常审查、高管报告，以及指标或查询逻辑的质量检查。

当困难部分是分析判断（指标定义、比较设计、解释或建议）时，优先使用此技能而非通用编码或电子表格帮助。

用户询问：分析数据、发现模式、理解指标、测试假设、队列分析、A/B 测试、流失分析或统计显著性。

## 核心原则

没有决策的分析只是算术。始终明确：**如果分析显示 X vs Y，会改变什么？**

## 方法优先

接触数据前：
1. **什么决策**需要此分析支持？
2. **什么会改变你的想法？**（真正的问题）
3. **你实际有什么数据** vs 你希望有什么数据？
4. **什么时间范围**是相关的？

## 统计严谨性检查清单

- [ ] 样本量充足？（小 N = 宽置信区间）
- [ ] 比较组公平？（相同时间段、相似条件）
- [ ] 多重比较？（20 次测试 = 1 次"显著"是偶然）
- [ ] 效应量有意义？（统计显著 != 实际重要）
- [ ] 不确定性量化？（说"12-18% 提升"而非仅"15% 提升"）

## 核心规则

### 1. 从决策开始，而非数据集
- 在进行分析前识别决策者、可能改变决策的问题和截止日期。
- 如果没有决策会改变，在做任何计算前重新构思请求。

### 2. 计算前锁定指标契约
- 定义实体、粒度、分子、分母、时间窗口、时区、过滤、排除和事实来源。
- 如果其中任何一项模糊，在呈现结果前明确说明模糊性。

### 3. 分离提取、转换和解释
- 保持查询逻辑、清理假设和分析结论可区分。
- 永远不要在 SQL、公式或笔记本代码中隐藏业务假设而不在报告中命名它们。

### 4. 选择视觉以回答问题
- 根据分析问题选择图表：趋势、比较、分布、关系、组成、漏斗或队列留存。
- 不要添加让演示看起来更满但不改变决策的图表。

### 5. 以决策格式简报每个结果
- 每个输出应包含答案、证据、置信度、注意事项和建议的下一步行动。
- 如果输出要发给利益相关者，将方法翻译为业务影响而非以技术细节开头。

### 6. 在推荐行动前压力测试声明
- 按明显混杂因素细分、比较正确的基线、量化不确定性、检查对排除或时间窗口的敏感性。
- 看起来很强的数字没有稳健性检查不是决策就绪的。

### 7. 数据无法支持声明时升级
- 样本量弱、来源不可靠、定义漂移或混杂未解决时阻止或降级结论。
- 说"尚不清楚"比产生虚假信心更好。

## 常见陷阱

- 更改分子、分母或排除后重用 KPI 名称 → 趋势比较变得无效。
- 在一个图表中比较日、周、月粒度 → 变化看起来真实但主要是聚合噪声。
- 显示百分比而无基础计数 → 管理层对小分母过度反应。
- 使用漂亮图表而非正确图表 → 输出看起来精致但隐藏实际决策信号。
- 看到结果后寻找有趣的切分 → 叙述跟随偶然而非证据。
- 发送没有指标负责人或注意事项的自动化报告 → 错误数字传播速度比纠正更快。
- 将观察模式视为因果证明 → 行动计划仅建立在相关性上。

## 方法选择

| 问题类型 | 方法 | 关键输出 |
|----------|------|----------|
| "X 与 Y 不同吗？" | 假设检验 | p 值 + 效应量 + CI |
| "什么预测 Z？" | 回归/相关 | 系数 + R² + 残差检查 |
| "用户如何随时间行为？" | 队列分析 | 按队列的留存曲线 |
| "这些组不同吗？" | 细分 | 轮廓 + 统计比较 |
| "什么是异常的？" | 异常检测 | 标记点 + 上下文 |

技术详情和何时使用每种方法，见 `techniques.md`。

## 输出标准

1. **以洞察开头**，非方法论
2. **量化不确定性** - 范围，非点估计
3. **陈述局限性** - 此分析不能告诉你什么
4. **建议下一步** - 什么会加强结论

## 需升级的危险信号

- 用户想"证明"预定结论
- 样本量太小无法可靠推断
- 使分析无效的数据质量问题
- 无法控制的混杂因素
